The problem

Automated remediation is dangerous in a way that testing usually misses.

PagedOut watches a set of microservices, works out what broke, and fixes it: drains a connection pool, clears a cache, rolls back a bad deploy. These are destructive actions against live infrastructure.

The failure people expect is that the system picks the wrong fix. The failures that actually hurt are subtler:

  • An acknowledgement is lost, the client retries, and the service restarts twice.
  • A process crashes, recovers from its checkpoint, and replays an action that already ran.
  • A rollback fires while a repair is still in flight and the two interleave.

Each of these needs one specific ordering out of millions. A test suite that runs two hundred times will never produce it. It will pass, and the bug ships.

Cannot observe is not the same as did not happen. The probe now retries, and an unresolvable state stops and escalates instead of retrying the action.

Both traces are regenerated from the seed on demand, not stored. Two runs of seed 3 produce byte-identical output on any machine — which is what turns a one-off failure into a permanent regression test.

The second bug

Seed 149. The one worth understanding.

Rolling back a deployment is self-inverse: do it twice and you are back where you started. When the network duplicated a rollback request, the service landed on the bad version again — and from the client's side that is indistinguishable from the action never having run. So it retried.

Fixing the verification logic was not enough; 95 violations survived. The real conclusion was structural:

Client-side idempotency keys cannot guarantee at-most-once execution. Once the network can duplicate a request, only the server can.

This is why Stripe and AWS implement Idempotency-Key on the server rather than trusting clients to retry carefully. The simulator found it in six seconds; it would have reached production otherwise.

How it works

Three layers. The third is the one that matters.

1 · INGEST checkout-service → payment-service → ledger-service logs · metrics · alerts ──► Kafka ──► Apache Flink 30-second event-time windows on RocksDB state 63 signals collapse into 1 incident 2 · DECIDE triage → investigate → retrieve runbook → plan → remediate live Prometheus · hybrid RAG over 1,342 documents every plan schema-validated against a closed action registry 3 · PROVE ← Groundhog virtual clock · seeded randomness · lossy network · crash injection 5 safety invariants checked against ground truth run(seed) → byte-identical trace, every time

The executor imports no clock, no random number generator and no HTTP client. Everything arrives through injectable ports. If even one source of nondeterminism were left hardcoded, no failing seed would reproduce and the simulator would be worthless.

Where this applies

PagedOut is a portfolio system, not a product. The technique underneath it is not.

Platform and SRE teams

Auto-remediation you can actually turn on

Most teams write runbook automation and then leave it in dry-run forever, because nobody can prove it won't double-execute during a partial outage. Simulating the execution path against injected faults is how that gets approved for production.

Teams shipping AI agents

Safety for agents that take real actions

An agent that calls APIs, moves money or changes infrastructure has the same at-most-once problem, and almost none of them test for it. Recording the model's decisions once and replaying them deterministically tests the execution machinery without re-rolling the dice on the model.

Anyone building distributed systems

Bugs that survive normal testing

Retry storms, replay after recovery, and duplicate delivery need exact orderings. Deterministic simulation is how FoundationDB and TigerBeetle find them, and it runs on a laptop with no cluster and no dependencies.

Engineering leaders

A regression test that cannot flake

Every bug found becomes a seed. It reruns in milliseconds, needs no infrastructure, and reproduces the exact interleaving forever. Timing-based chaos testing cannot offer that, which is why teams end up ignoring it.
